## One data layer, two TAW themes

`taw/core` is TAW's data layer. It defines your content model (post types, taxonomies, fields,
options pages), stores values as post, term and user meta and options, exposes them over the REST API, and moves
them between environments with [Content Interchange](/content-interchange). You don't need ACF,
Carbon Fields or any other plugin.

Two themes consume it:

| Theme | Kind | Boots |
|---|---|---|
| [TAW Theme](/taw-theme) | Classic, with PHP blocks, Vite, Tailwind and Alpine | `Theme::bootstrapFullSite()` — the data layer **plus** the classic-theme toolkit |
| [TAW Gutenberg](/taw-gutenberg) | Block (full site editing) theme | `\TAW\Core\Boot::data()` — the data layer **only** |

<Callout kind="info">
  `taw/core` is built for TAW sites only (taw-theme, taw-gutenberg and their child themes). It isn't a general-purpose plugin API for third-party themes.
</Callout>

## Boot the data layer

A classic TAW theme already gets it: `Theme::boot()` calls `Boot::data()` itself. A data-only theme
calls it directly, after requiring the Composer autoloader:

```php functions.php
require_once __DIR__ . '/vendor/autoload.php';

\TAW\Core\Boot::data();
```

`Boot::data()` registers the Tools → TAW Data import/export screen, the content export REST route,
REST-registered field meta, and the schema registry described below. It adds **nothing to the front
end**: no Vite, no Alpine, and no performance tweaks, so a block theme keeps Gutenberg's block CSS.
Calling it more than once is harmless.

<Callout kind="alert">
  Since `taw/core` v1.42.0, the Performance optimizations (which dequeue the block library CSS, among other things) register only when `Theme::boot()` or `Theme::bootstrapFullSite()` runs, not when the autoloader loads. If a setup relied on the old behavior without ever calling `boot()`, add `define('TAW_PERFORMANCE_AUTOLOAD', true);` to `wp-config.php`.
</Callout>

## Define data in PHP

Hook into `taw_schema_register`. It fires on `init`, so translation functions are safe:

```php
use TAW\Core\Schema\{Field, Registry, Schema};

add_action('taw_schema_register', function (Registry $schema): void {
    $schema->add(Schema::postType('book')->labels('Book', 'Books')->args(['menu_icon' => 'dashicons-book']));
    $schema->add(Schema::taxonomy('genre')->for('book')->labels('Genre', 'Genres'));
    $schema->add(
        Schema::fieldset('book_details')->title('Book details')->on('book')->fields([
            Field::text('book_author')->label('Author')->required(),
            Field::image('book_cover')->label('Cover'),
            Field::repeater('book_awards')->fields([Field::text('name')->label('Award')]),
        ])
    );
    $schema->add(Schema::optionsPage('library')->title('Library settings')->fields([Field::text('library_phone')]));
});
```

A fieldset compiles into a regular `Metabox`, and an options page into an `OptionsPage`. Storage, the
admin UI, REST and content export work exactly like hand-written ones. `Field::*` builders produce the
same arrays that `new Metabox([...])` accepts, so you can mix builders and raw arrays, and
`->with([...])` passes through any option the builder has no method for.

## Define data in JSON

Put one entity per file in a `taw-schema/` folder. Subfolders one level deep are fine
(`taw-schema/post-types/book.json`). The keys use the same words as the PHP API:

```json taw-schema/book-details.json
{
  "$schema": "../vendor/taw/core/resources/schema/taw-schema-1.0.json",
  "version": 1,
  "kind": "fieldset",
  "key": "book_details",
  "title": "Book details",
  "on": ["book"],
  "fields": [
    { "id": "book_author", "type": "text", "label": "Author", "required": true },
    { "id": "book_awards", "type": "repeater", "fields": [{ "id": "name", "type": "text" }] }
  ]
}
```

| `kind` | Keys (besides `version`, `kind`, `key` and optional `override`) |
|---|---|
| `post_type` | `labels` (`singular`, `plural`), `args` — passed to `register_post_type()` |
| `taxonomy` | `for` (post types, required), `labels`, `args` — passed to `register_taxonomy()` |
| `fieldset` | `on` (required: post types, `term:<taxonomy>` or `user`), `fields` (required), `title`, `context`, `priority`, `prefix`, `ui` (`panel` or `metabox`, see [Data panel](/data-panel)), `config` |
| `options_page` | `fields` (required), `title`, `menu_title`, `capability`, `rest` (`private` or `public`, see [below](#options-pages-over-rest)), `config` |
| `settings` | Key must be `site`. `fieldsetUi`: where fieldsets show in the block editor unless they set `ui` (see [Data panel](/data-panel)) |

The `$schema` line gives your editor autocomplete and inline errors. A typo in a top-level key is an
error. Extra keys on a field, like `conditions` or `width`, pass through to the field engine.

### Where files are found, and which one wins

Folders are scanned in this order: the child theme's `taw-schema/`, the parent theme's `taw-schema/`,
then `wp-content/taw-schema/` for site-level definitions that should survive a theme switch. When the
same entity is defined twice, **PHP beats every JSON file**, a child theme beats its parent, and a
theme beats `wp-content`. Set `"override": true` (or `->override()` in PHP) to mark a replacement as
deliberate. Otherwise you get a debug notice.

An invalid file is skipped with a notice, and the rest still load. In production, parsed files are
cached until one of them changes.

### Validate without WordPress

```bash
php bin/taw schema:validate            # this theme's taw-schema/
php bin/taw schema:validate path/ --json
```

It exits with an error on invalid files, pointing at each problem (for example
`/fields/2/type: must be one of text, url, …`). It also warns about duplicates, and about fieldsets or
taxonomies that target a post type these files don't define. Run it in CI.

## Defaults and rules

<ExpandableGroup>
  <Expandable title="Post type and taxonomy defaults" default-open="false">
    Post types default to `public` and `show_in_rest`. **`custom-fields` support is always added**, even when you pass your own `supports`: WordPress hides registered meta from REST without it, so your fields would silently disappear from `wp/v2`. Taxonomies default to `show_in_rest`. Everything else comes from `args`.
  </Expandable>

  <Expandable title="Reserved and invalid keys" default-open="false">
    Keys are validated up front. Core names like `post` or `page` are rejected, and so are keys over WordPress's length limits (20 characters for post types, 32 for taxonomies) and taxonomies named like public query vars, such as `year` or `author`.
  </Expandable>

  <Expandable title="Field ids: qualified, but still namespace them" default-open="false">
    Since `taw/core` v1.52.0, every field also has a qualified id, `"{fieldset}.{field}"` (group sub-fields `"{fieldset}.{group}_{sub}"`). REST meta, content export and import, the data panel, the visual editor and `bin/taw fields:get` / `fields:set` look fields up per post type (or taxonomy, or users) through it, so two fieldsets can share a field id and each keeps its own type and sanitizer. `Metabox::fieldsFor('post', 'book')` lists the fields stored on a post type.

    The bare-id helpers are still ambiguous: `Metabox::get_field_config($id)` keeps one entry per id, and on a post type with both, `Metabox::get($postId, $id)` reads the `_taw_` one. So a shared id is still reported with a debug notice (and an admin notice when `WP_DEBUG` is on). Prefix ids by entity (`book_author`, not `author`).
  </Expandable>

  <Expandable title="Timing" default-open="false">
    Definitions are collected on `init` priority 1, and the registry freezes at priority 5 (a later `add()` is refused with a notice). Post types register at 5, taxonomies at 6, and fieldsets and options pages at 8.
  </Expandable>

  <Expandable title="Permalinks" default-open="false">
    When your post types or taxonomies change, rewrite rules are flushed once, on the next admin request. You never need to re-save Settings → Permalinks, and the front end never flushes.
  </Expandable>
</ExpandableGroup>

## Read the data

Values are post meta named `_taw_<field id>`:

```php
use TAW\Core\Metabox\Metabox;

$author = Metabox::get($postId, 'book_author');
$awards = Metabox::get_repeater($postId, 'book_awards');   // decoded rows
```

Over REST, fields appear under `meta` (for example `/wp-json/wp/v2/book/42`), and structured fields
also appear decoded as `taw_<field id>`.

For typed values (images, rows, posts, links, escaped when echoed), use `Taw::post()`; see
[Reading fields](/reading-fields).

## Fields on terms

Target a taxonomy's terms with `term:<taxonomy>` in `on`, alone or next to post types (`taw/core`
v1.53.0+):

```json taw-schema/genre-details.json
{
  "version": 1,
  "kind": "fieldset",
  "key": "genre_details",
  "on": ["term:genre"],
  "fields": [
    { "id": "genre_tagline", "type": "text", "label": "Tagline", "required": true },
    { "id": "genre_cover", "type": "image", "label": "Cover" }
  ]
}
```

- The fields show on the taxonomy's **Add** and **Edit** screens, with every field type, conditions,
  read-only fields and validation, exactly as on a post. Saving needs the `edit_term` capability.
- Values are term meta (`_taw_genre_tagline`). Read them with `Metabox::get_term($termId, 'genre_tagline')`,
  or `Metabox::term($termId)` for typed reads: `->bool()`, `->repeater()`, `->imageUrl()`, `->color()`,
  `->posts()`, `->gradientText()`.
- Over REST they're under `meta` on the term (`/wp-json/wp/v2/genre/7`), with the decoded `taw_<field id>`
  for structured fields. On `post_tag`, the REST type is `tag`.
- [Content snapshots](/content-interchange) carry them as the term's `fields`.
- The [data panel](/data-panel) is for posts only; term screens always use the metabox form.

`schema:validate` warns when the taxonomy isn't defined by your schema files or by WordPress.

## Fields on users

`user` in `on` puts a fieldset on **Profile**, **Edit User** and **Add New User** (`taw/core`
v1.54.0+):

```php
$schema->add(Schema::fieldset('author_details')->on('user')->fields([
    Field::url('author_website')->label('Website'),
    Field::repeater('author_links')->fields([Field::url('href')->label('Link')]),
]));
```

- Every field type, condition and validation works, as on a post. Saving needs the `edit_user` capability.
- Values are user meta. Read them with `Metabox::get_user($userId, 'author_website')` or
  `Metabox::user($userId)->repeater('author_links')` (the same typed reads as terms).
- **Over REST, user fields are private:** they appear only in the `edit` context, to people who can edit
  that user. They never show on an author's public `/wp-json/wp/v2/users/<id>`.
- [Content snapshots](/content-interchange) carry them with `--with-users`.

## Options pages over REST

Options pages are private by default. A page opts in with `rest` (`taw/core` v1.55.0+):

```json taw-schema/site-settings.json
{
  "version": 1,
  "kind": "options_page",
  "key": "site",
  "rest": "public",
  "fields": [{ "id": "company_phone", "type": "text", "label": "Phone" }]
}
```

```php
Schema::optionsPage('site')->rest('private')->fields([/* … */]);
```

| `rest` | Where | Who |
|---|---|---|
| *(not set)* | Nowhere | — |
| `private` | `/wp-json/wp/v2/settings`, keyed by option name (`_taw_company_phone`). Read and write | Administrators (`manage_options`) |
| `public` | The above, **plus** `GET /wp-json/taw/v1/options/<page id>`: every field by id, decoded like REST post fields (checkbox `true`/`false`, repeaters as arrays) | **Anyone, no login** |

Writes through `/wp/v2/settings` get the page's own validation (`required`, URLs, number `min`/`max`,
custom `validate`): a bad value returns a `400` naming each option, and the old value is kept.

<Callout kind="alert">
  A `public` page publishes **every field on it**. Never put API keys, internal emails or anything private on it. Keep secrets in `wp-config.php` constants whatever the page's `rest` setting.
</Callout>
